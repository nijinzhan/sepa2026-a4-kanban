## 2. 实际运行库并未安装全部官方迁移

本机沿用`a4-lihong-postgres-20261031`中的A-5数据库。安装日志包括bootstrap、V1—V13和五个R__脚本，共19项；19项安装摘要和来源引用均与当前P-Blue main一致。本轮还直接提取运行库函数体，与GitHub固定版本逐项比较，以下四项一致：

- `asr.fn_transcript_before_update`
- `asr.fn_transcript_after_write`
- `asr.fn_apply_transcript_edit`
- `anno.fn_build_export_items`

但是，初始化工具明确只应用V1—V13，漏装官方`V14__backup_and_restore.sql`，运行库没有`ops.db_backup`。因此不能把该库称为“GitHub所有迁移均已安装”。此前使用“最新”时应限定到已核验源码和相关函数，而非全量运行库。

团队最新交付中，尹凯臣目录的八个同名迁移与P-Blue版本一致；刘希睿src/代码两份V14备份迁移也与P-Blue官方V14一致，未提供转写修订或导出函数的新修正。近期操作手册、清理验证和验收报告更新不能自动视为业务函数升级。

本地P-Blue另有未跟踪的`V14__a4_revision_and_contract_compatibility.sql`，是10/24的兼容修订草案，既不在当前远端main中，也未装入本机库。它与官方V14备份迁移编号冲突，不能将它当作GitHub最新交付或直接混装。后续若采用其中方案，应经过复核并安排新的迁移编号。

## 3. 官方V14回滚验证

为核实漏装迁移是否影响问题判断，本轮从固定Git引用读取官方V14，在强制回滚事务内实际执行；没有调用备份清理或恢复函数。

| 核对 | 结果 |
|---|---|
| 官方V14能否在当前库执行 | 成功，事务内可查到ops.db_backup |
| 是否修改导出函数 | 未修改，函数体前后一致 |
| 原长片段大小计算 | 仍复现SQLSTATE 22003 |
| 提前转换bigint的只读对照 | 结果1762080字节；只验证计算式，不冒充完整导出修复通过 |
| 是否新增带期望版本的CAS修订函数 | 没有，fn_apply_transcript_edit_cas仍不存在 |
| 事务结束后库状态 | V14对象已回滚；用户录音两条文本的行指纹前后一致 |

因此，运行库确实有一个迁移缺口，但官方最新V14不会自动修复本次人工修订和长片段导出问题。
