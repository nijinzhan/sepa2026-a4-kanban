# ASR容器与512 MiB内存验证

日期：2026-11-03。负责需求：RQ-A-4-10、RQ-A-4-20。

**结论：现有教师SenseVoice INT8可以在Linux Docker容器内执行真实识别；512 MiB不能稳定覆盖本次工作负载。两次独立进程测试均先完成5次20秒识别，再在120秒音频处理中被OOM终止。1024 MiB扩展对照完成了全部推理尝试且无OOM，但有片段触发空文本保护，不能记为整段转写通过。**

这是本机可行性验证，测试镜像与脚本为实验用途；没有切换日常联调部署，没有连接数据库或真实团队上游，也不构成长期稳定性或模型质量验收。

## 2. 输入与执行顺序

- 短样本：此前本机联调所用真实VHHH C15前20秒，16 kHz单声道WAV，SHA-256为`8abfc46c7f036f62e25808810b7d734ee432287a670e602ad8f1d42c5daef33b`。
- 长样本：从本机现有C15录音截取前120秒，16 kHz单声道PCM16 WAV，SHA-256为`68d1c172b7ea0cd99858be7cedaeb201112ee34e84cc968af3bad7b2789afabe`。截取保留原样本顺序，没有合成或循环拼接。
- 每个容器启动全新Python进程，校验实际模型身份并加载；串行执行5次20秒解码、分段和逐段真实识别，再执行一次120秒处理。全新进程不等于清空宿主机文件缓存。
- 原1 GiB探针遇空文本异常按现有规则停止。扩展探针为覆盖后续内存负载，记录空文本异常并继续尝试剩余片段；这只是实验策略，未修改真实工作服务遇首个失败即停止的业务规则。
- 推理使用现有WebRTC分段及教师SenseVoice CPU实现，保留每次音频长度、片段数、耗时、进程RSS高水位和cgroup内存信息；正式摘要不含识别原文或音频。

首次两次预检在测试脚本的旧样本指纹断言处停止，当时模型已加载但尚未识别；已固定实际样本指纹后重跑。预检不计入本节正式内存结论，原日志单独保留。

## 3. 实际结果

| 限额与容器 | 结果 | ExitCode | OOMKilled |
|---|---|---:|---|
| 512 MiB / a4-lihong-asr-512m-cold1 | 5次20秒识别通过；进入120秒处理后被OOM终止 | 137 | true |
| 512 MiB / a4-lihong-asr-512m-cold2 | 5次20秒识别通过；进入120秒处理后被OOM终止 | 137 | true |
| 1024 MiB / a4-lihong-asr-1024m-compare | 5次20秒识别通过；120秒处理中触发空文本保护，非OOM | 1 | false |
| 1024 MiB / a4-lihong-asr-1024m-extended | 5次20秒识别通过；120秒全部推理尝试完成，空文本另记 | 0 | false |

512 MiB两次均在完成短样本后进入长样本测试，没有完成120秒识别。Docker的`OOMKilled=true`与退出码137共同确认内存终止；不将一般参数错误、样本校验失败或程序异常当作OOM。当前日志只定位到120秒处理阶段，未细分断言具体在哪个底层分配点终止。

1024 MiB扩展对照中：5次短请求各返回2段非空识别文本；120秒样本共尝试6段，5段返回非空结果，1段触发既有空文本保护，耗时19.183秒。整段转写不能记为通过。cgroup记录的内存峰值为**610.76 MiB**，进程RSS高水位为**665.11 MiB**。两者记账范围不同，不能直接相加。失败容器的最后一次日志在OOM前，最后上报峰值不代表终止时峰值。

另以1024 MiB启动现有个人FastAPI工作服务：`GET /health`返回200及`{"status":"ok"}`，`GET /openapi.json`返回200，接口版本0.2.0，实际包含转写、保存、读取和修订入口。此次HTTP检查只验证工作服务可启动；真实ASR由前述推理实验验证，没有把健康检查当作完整转写/保存联调。

HTTP启动检查发现：原HTTP模式直接启动时，初始`current_trace_id()`为空，被httpx拒绝作为请求头值；这是启动上下文问题，不能解释为内存不足。实验使用`start_http_probe.py`在调用原入口前建立初始追踪上下文，随后健康检查通过，未修改个人源码。HTTP检查镜像ID为`sha256:6f096c315863f1c7aca6d487030d80d1591b2c14c25d8ace72bd0cdbe504145f`，比扩展推理镜像仅增加此启动包装器。正式迁移时应保留等效的初始化方式或修正原入口，并单独回归；本次不宣称原HTTP入口可以不经调整直接部署。

## 4. 使用判断与限制

1. **可以容器化。** Linux依赖安装、同一权重加载、实际分段识别及原HTTP工作服务启动均有本次证据。
2. **当前不能按512 MiB稳定部署。** 短音频能运行不足以证明稍长音频或完整服务可持续工作；本轮已有两次明确反例。将进程装入容器不会自动缩小模型运行内存。
3. **1024 MiB完成本轮内存负载测试，不是最小内存或整段功能通过的证明。** 若迁入日常联调，可作为下一轮起点；更长录音、目标并发、服务运行时间及目标CPU仍需测量。没有验证512与该预算之间的全部值；增加内存也不保证消除识别空文本。
4. **保留现有模块边界。** 业务后端512 MB预算与独立ASR资源分别配置；数据库容器及数据卷保持原状。不能因为ASR另开容器就认为仍共用业务后端512 MB限额。
5. **512 MiB若不可调整，需要另作优化再测。** 可评估更小模型、受控切段及解码内存、推理运行时配置；本次没有实施这些变更，不能保证其中某项单独就能达标。
