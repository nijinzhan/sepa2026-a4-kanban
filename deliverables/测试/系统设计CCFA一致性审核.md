## 4. 主要优势

1. **约束有适用范围。** §4.11、§7.2及§8.2.1区分单次处理上限、公共库存量和平台阈值，也区分模型互斥、记录并发和资源负载，避免由一条限制推导出整个系统停用。
2. **反馈与保护相互衔接。** §4.6/4.11在登记和推理前拒绝超限，§5/6.2分开保存失败与未确认；原文、版本、来源及历史保护没有因放宽规模而取消。
3. **目标与事实分开。** §2.7、§4.13及§5.13保留待定项；§4.12/5.12将新增边界与负载场景明确作为后续测试计划。
4. **图文主线一致。** 八张图无需重画；图4-1以图注承接校验内涵，三张存取时序图位于对应流程小节，Word图片和图题同页。

## 5. 写作问题与严重程度

以下严重程度记录问题修正前的影响，不表示 V0.9 仍存在同等问题。

### C001: 转写专用门禁曾泛化到所有 HTTP 操作

Type / 类型: confirmed_flaw

Severity / 严重程度: major

Location / 位置: V0.5 §7.2；当前§3.1、§4.11—4.12、§5.12、§6.2、§7.2、§9.1及附录A。

Evidence / 证据: 旧稿以“每次HTTP调用”统领转写幂等键与互斥，与仅转写要求该键的接口说明、需求§5.4冲突。V0.8已分为共同校验、四操作控制和转写回执；V0.9保留此划分。

Countercheck / 反证复核: 逐项对照四操作及429范围；保存、读取和修订均不取得模型锁，公共记录的事务或版本等待有独立说明。未发现其他章节仍要求共用模型门禁的反例。

Judgment / 判断: 原有适用范围冲突已消除；文本操作可能等待同一记录的事务，不等于等待转写模型锁。

Criterion / 维度: Method readability；Reviewer-facing risk。

Resolution / 解决或改判条件: 保持四操作规则一致；后续新增公共门禁时重新核对需求§5.4。

Status / 状态: resolved

### C002: 容量要求曾缺少设计责任与反馈落点

Type / 类型: confirmed_flaw

Severity / 严重程度: minor

Location / 位置: 需求§3.4；当前§2.1.4、§4.12、§5.12、§8.2.1、§9.1—9.3及附录A。

Evidence / 证据: V0.5未完整承接容量增长、告警与限制规则。V0.8已明确全项目共享10GB、至少30%年增长余量、80%告警及90%暂停非必要批量下载和新增大文件任务，并补责任、拒绝和恢复核对。

Countercheck / 反证复核: 对照三方责任，未把公共监控交给个人模块；告警、明确拒绝、提交未知也未混同。读取、修订及常规小额保存不因阈值一律禁用。

Judgment / 判断: 容量需求已有设计和验证落点；平台是否实际提供监控与准入仍须后续确认。

Criterion / 维度: Claim-evidence alignment；Terminology and notation consistency。

Resolution / 解决或改判条件: 维持公共平台职责与个人反馈边界，平台定版后补真实契约证据，不将设计记为平台验收。

Status / 状态: resolved

### C003: 固定500段容易被理解为不可调整的需求上限

Type / 类型: clarification

Severity / 严重程度: minor

Location / 位置: §4.6、图4-1图注、§4.11—4.13、附录A；对照§6.2.1及需求§3.2.2、§3.4。

Evidence / 证据: V0.8写固定500段，需求未规定该固定值。V0.9改为部署配置maxSegments，正整数、原型默认500，启动校验、单次冻结并记录；VAD后超限返回422/JOB_SEGMENT_LIMIT，先于登记、新建识别任务和推理。

Countercheck / 反证复核: 当前转写请求只接收录音标识，不能推断已支持时间范围或片段列表，也不能用新幂等键绕过超限。正文保留A-3及编排方提供可追溯分批输入的前提，没有虚构自动分批能力。默认500仍需代表性录音与目标资源实测。

Judgment / 判断: 固定值已降为原型默认值，检查顺序、反馈及后续处理责任清楚；仍保留单次资源保护，未误写成公共库存量上限。

Criterion / 维度: Method readability；Claim-evidence alignment。

Resolution / 解决或改判条件: 后续实现配置校验，按N−1/N/N+1及非法配置验证；分批输入与来源关联定版后再追加自动分批结论。

Status / 状态: resolved

### C004: 非阻塞与模型失效时的可用性承诺需要条件

Type / 类型: unsupported_claim

Severity / 严重程度: minor

Location / 位置: §4.11—4.12、§5.12、§7.1、§7.2.1、§9.2；对照§2.1.2.2。

Evidence / 证据: 旧稿对识别环境不可用时仍可读取、修订的表述缺少工作服务仍在运行的条件，也容易将“不占模型门禁”理解为没有资源等待。V0.9明确工作服务、公共数据服务及资源可用前提，不承诺任意负载下立即响应。

Countercheck / 反证复核: 检查运行组合、降级措施、并发测试及性能要求，均区分模型锁、同记录事务等待和共享资源竞争；工作服务整体退出须先恢复。CPU、内存、线程、网络与公共服务负载没有被排除在条件之外。

Judgment / 判断: 承诺已收窄到操作控制边界，并以实际延迟、错误和负载记录作为后续验证依据；资源竞争不能一概误报为模型忙429。

Criterion / 维度: Claim-evidence alignment；Reviewer-facing risk。

Resolution / 解决或改判条件: 按§2.1.2.2约定条件测量，分别记录门禁等待与响应表现；没有目标负载证据时不得升级为无条件性能保证。

Status / 状态: resolved

## 8. 作者关键问题与改判条件

- [C003] **500应调到多少？** 材料不足以给出更高固定值。保留原型默认500、允许部署调整，目标机器和代表性录音实测后再确定。
- [C003] **超限能否立即自动分批？** 当前接口不足以支持这一结论。须确认A-3、编排方的分批输入及源录音/时间/片段关联；当前只承诺明确反馈和后续安排。
- [C004] **文本操作能否始终快速完成？** 不能从模型锁独立推得无条件性能保证。应按约定负载测量，并区分同记录事务、资源竞争和公共服务异常。
- **是否还有待处理的文字缺陷？** [C001]—[C004]已在设计层面处理。可配置上限尚未实现，公共鉴权、事务、业务关联和VHHH质量待验证，属于实现或验收事项；不据此要求设计必须已经实现。
