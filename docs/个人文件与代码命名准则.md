## 1. 评价标准明确要求什么

评价标准第1页“个人工作评价 → 课程报告 → 是否体现个人工作”列出三项：

1. “个人负责开发模块代码以独立文件保存，文件名以下划线加学号结尾”。
2. “顶层控制逻辑代码文件中，不同个人实现的函数、类命名以下划线加学号结尾”。
3. “未添加个人标识的代码，不计入个人工作量”。

因此，普通个人源码文件采用 `职责名称_2024141460331.py`，学号位于扩展名前；顶层控制代码中的个人函数、类采用 `原名称_2024141460331`。个人目录名、Git 提交记录和作者注释可以辅助追溯，不能替代原文指定的文件名及函数、类后缀。

原文没有要求给所有变量、参数、业务字段、文档或配置文件加学号，也没有规定所有函数和类都必须加学号。“顶层控制逻辑”指组织调用和业务流程的控制代码，不能直接等同于 Python 文件中所有模块级定义。

## 4. 固定入口、协议与公共接口如何处理

### 4.1 Python固定文件与协议方法

`__init__.py`、`__main__.py` 应保留 Python 识别的固定文件名。`__init__`、`__post_init__`、`__call__` 等协议方法也保留原名，否则解释器或框架将无法按原协议调用。

采用的处理办法：固定入口只保留包说明或最小调用，把实质业务实现放入带学号的普通模块；在固定文件及协议方法所在类中保留清楚的个人归属说明。当前 `__main__.py` 调用：

```python
from .cli_2024141460331 import main_2024141460331

raise SystemExit(main_2024141460331())
```

这是兼顾语言机制与个人归属的技术处理办法。评价标准没有写明这些固定名称的例外，不能声称教师已明确豁免；报告中如实列出固定入口及其所调用的个人实现，供工作量核查。

### 4.2 公共接口和第三方名称

Python内部名称与接口字段可以采用不同形式。例如内部参数 `business_task_id` 对应 JSON 字段 `businessTaskId`，是既有接口映射。公共字段、URL、数据库字段、模型文件名、第三方库接口及第三方原始代码按现有契约或来源保留，不擅自追加本人学号。

本人编写的适配文件按个人源码文件规则命名。文件中涉及第三方来源时，说明来源与本人修改范围；给文件加学号不代表其中第三方实现属于本人工作量。

## 6. 后续新增和提交前如何检查

新增代码时先确定职责和归属：普通个人源码与测试文件带完整学号；顶层控制文件中的个人函数、类按第3节处理；固定名称和公共契约按第4节处理。文档保持用途可辨和路径稳定。

提交前核对四件事：

1. 本人新建或更名的普通代码文件是否带 `_2024141460331`，顶层控制代码中的个人符号是否采用约定后缀。
2. 固定名称是否保持有效，个人归属、第三方来源及修改范围是否可查。
3. 改名引用是否更新完整，命令入口、导入、测试收集及回归检查是否通过。
4. 变更是否仅涉及本人目录，说明文档是否与实际路径一致。

现有 Ruff 仅启用 `E、F、I、B、UP`，并不检查课程学号后缀；因此此前 Ruff 通过不能证明个人标识符合评价要求。后续如增加自动检查，应单独核对普通代码文件及控制符号后缀，并对固定入口、协议方法和外部契约保留明确处理规则；不直接套用会拒绝课程专用类名后缀的通用规则。
